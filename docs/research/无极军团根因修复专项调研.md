# 无极军团 · 根因修复矛盾专项调研（治本 vs 治标）

> 版本：v1.0
> 日期：2026-08-15
> 背景问题（用户提出）：根因官的设计初衷是"治本"——每次发现 bug 找到根因修复，不打补丁套补丁（否则屎山/定时炸弹）。但实际应用发现：为了找根因，把简单任务无限拖长。
> 核心矛盾：**治本（找根因，防复发）** vs **快（不拖长任务）**。

---

## 一、矛盾的本质（白帽判断）

您设计的根因官，方向是对的（治本防补丁套补丁），但落地时缺了一个关键开关：**不是所有 bug 都值得追根因，也不是所有根因都要无限追下去**。

问题不在"要不要找根因"，而在"**何时深挖、何时止步**"。之前是"要么不找（打补丁）、要么无限找（拖死）"两个极端，缺中间的**分级止步机制**。

### 2.3 复发驱动的根因（关键触发机制）

| 来源 | 机制 | 借鉴点 |
|---|---|---|
| [Breaking the Cycle of Recurring Failures（ICSE 2025）](https://conf.researchr.org/details/icse-2025/aiops-2025-papers/10/Breaking-the-Cycle-of-Recurring-Failures-Applying-Generative-AI-to-Root-Cause-Analys) | 用生成式 AI 打破"反复失败循环"——重点在**复发** | **根因分析应该由"复发"触发，不是每次 bug 都触发** |

## 三、无极军团的方案（治本 + 快，两全）

**核心设计：根因官 = 复发驱动的分级止步机制，不是"每次 bug 都无限追"**

### 分级规则

```
发现 bug
  → 先快速修复（治标，不打补丁套补丁的"脏修复"，而是最小正确修复）
  → 记录 bug 指纹（症状 + 修复 + 位置）
  → 若这个 bug 是【第一次出现】→ 到此为止（治标，但记录在案）
  → 若【同类 bug 第二次出现】（复发）→ 触发根因官深挖（治本）
  → 根因官深挖【有界】：四阶段结构化 + 深度上限，不无限追
  → 找到根因 → 治本修复，并把根因+修复沉淀进经验库
```

### 关键机制（白帽钉死，防两个极端）

1. **根因官不是每次 bug 都出场，而是"复发才出场"**：第一次快修 + 记录，复发了才深挖。这样简单 bug 不拖长，反复 bug 才治本。
2. **快修 ≠ 补丁套补丁**：快修是"最小正确修复"（最小改动解决问题，不引入新问题），不是"随便糊一下"。补丁套补丁的根源是"没记录、没复发追踪"——我们加了 bug 指纹记录，第二次出现就会暴露是同一个根因，自然转深挖。
3. **根因深挖有界**：四阶段结构化（复现→定位→假设→验证）+ 深度上限（如最多 5 层"为什么"），找到可验证的根因就停，不无限追"根因的根因"。
4. **严重 bug 例外**：高风险/影响面大的 bug，即使第一次出现也直接深挖根因（按严重程度分级，不是一刀切）。

### 对应之前的设计修正

之前我们定的"失败重派有熔断（3 角度/5 次）"，现在补充为**更精细的 bug 处理流程**：
- 简单 bug：快修 + 记录（不触发根因官）
- 复发 bug：触发根因官，有界深挖（治本）
- 严重 bug：直接根因官深挖

## 四、DSH 落点

| 机制 | DSH 落点 |
|---|---|
| bug 指纹记录 | 根因官的经验库（sessionProjections 或记忆文件） |
| 复发检测 | 同指纹 bug 再次出现时，匹配经验库命中 |
| 根因官触发 | 复发时契约自动触发（独立官员的触发机制） |
| 有界深挖 | 根因官职权模板内置"四阶段 + 深度上限"约束 |
| 治本修复沉淀 | 根因 + 修复方案写入经验库，下次直接复用 |

## 五、结论

**您的根因官设计是对的（治本防屎山），缺的是"复发驱动 + 有界深挖"这个开关。** 加上后：
- **简单 bug 不拖长**：第一次快修 + 记录，根因官不出场。
- **反复 bug 才治本**：第二次出现才深挖根因，一次修到底。
- **治本不无限**：深挖有界（四阶段 + 深度上限），不追"根因的根因的根因"。
- **补丁套补丁被根除**：因为有 bug 指纹记录，同类 bug 第二次必然暴露是同一根因，逼着走治本。

**一句话**：根因官从"每次 bug 都出场"改成"**复发才出场、出场就有界**"——治本的目标不变，但不再为治本拖死简单任务。
