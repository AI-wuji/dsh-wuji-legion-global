# 一、初衷（一切的根本，完整保留）

> **让不了解插件、Skill、MCP 是什么的小白用户，在遇到问题时，由系统级的无极军团自动调用相对应的能力去执行任务，而不需要用户手动去选择具体要用什么 Skill 或 MCP。**

> **同时，把同类型的能力复制、蒸馏、融合，整合成能力更强的新插件，以更快的速度、更高的质量为用户服务。**

**初心拆成两条支柱：**

1. **系统级自动调用（无感）**——用户只说人话，系统自己决定"该用什么能力"，全程不让用户接触"skill / 插件 / MCP"这些概念。
2. **能力进化重生（越用越强）**——把同类的 skill / 插件 / MCP **复制、蒸馏、融合**成更强的新能力，比原来的更快、更好。融合不是叠加（把几个并列塞一起）、不是替换（只留最强的），而是**查漏补缺、取长补短地重生**成一个新物种——不属于任何一个前身。

**这两条是判断一切的尺子**：任何设计如果让用户去选技能，就是违背初心①；任何融合如果是"叠加"或"只留最强"，就是违背初心②。

# 一·五、三大通病：从源头堵死，不让它发生

> 无极军团之前版本的三个通病（上下文超大、任务耗时久、融合不如不用）。这次**不是靠防御**（事后检测、拦截、补救——被动、易被绕过、还耗资源），而是**从机制设计上就不让它有发生的机会**。下面对每一条，都只回答一个问题：**为什么在新体系里，这件事在结构上就根本不会发生。**

## 通病一：上下文超大 —— 结构上就不允许全量进入

**旧机制为什么发生**：模型每轮都要拿到"完整历史 + 全部技能说明 + 全部工具定义"，上下文天然越聊越大——这是**结构缺陷**，靠"压缩""裁剪"去补救就是防御。

**新机制为什么不会发生**：
- **表结构本身就只装"框架+当前项"**：每岗位一张表，模型每次只拿到"整张表标题 + 当前处理那一项"。这不是"大了再减"，而是**表从第一次被读起，就只以最小形态进入上下文**——全量数据从一开始就躺在冷存储里，根本没有进入上下文的通道。
- **记忆只写回有用的**：会话结束时，只把"这次验证过有用的方法"写成一条记忆；没用的**从不进入存储**——不是存了再清理，是压根不存。
- **技能只挂一句话**：技能目录默认只有"名字+一句话"，详细内容物理上就是按需展开的另一个文件——**未选中的技能，在结构上就不在上下文里**。
- 结论：上下文的"大"没有来源——每个进入上下文的东西，都是被当前任务点名的、最小的那一份。

## 通病二：任务耗时久 —— 结构上就不存在绕路

**旧机制为什么发生**：所有任务都走"生成→检查→重做→再检查"的完整链路，简单事也绕大圈；串行执行；失败无限重试——这是**流程结构缺陷**，靠"监控时长""熔断截停"补救就是防御。

**新机制为什么不会发生**：
- **直道是默认路径**：简单任务在结构上就直接在主线程完成，**根本不经过参谋部的复杂流程**——不是"检测到简单任务再走捷径"，而是"除非需要复杂调度，否则根本不会进入慢路径"。
- **规矩立在开工前**：做什么、不做什么、做到什么算好，在任务启动那一刻就锁死进契约。**做完之后没有"检查重做"这个环节**——因为该限制的东西在生成前就已经定死了，生成时就被约束着，不存在"做完发现错了"。
- **并行是默认调度方式**：无依赖的任务在结构上就是同时派发的，不存在"排队等"。
- **重试有先天上限**：每个子任务开工时，它的"最多试几次、最多换几个角度"就已经写在任务单上——不是"发现重复了再截停"，而是**从派发那一刻起，循环次数就是有界的**。
- 结论：慢的每一个来源（绕路、返工、串行、死循环），在新体系里都**没有对应的结构**。

## 通病三：融合不如不用 —— 结构上就产出不了"更差"的东西

**旧机制为什么发生**：融合 = 把几个父代规则并列塞一起（堆叠），或只留最强的（替换）——这是**融合方式的错误**，靠"事后对照""回滚"补救就是防御。

**新机制为什么不会发生**：
- **融合的定义就是"重生"**：查漏补缺、取长补短，生成一个不属于任何前身的新物种。**堆叠和替换，在定义上就被排除了**——它不是"融合做错了再纠正"，而是"按这个定义做，根本做不出堆叠"。
- **互补矩阵是动工前的设计图**：父代优点/缺点、新决策结构怎么取长补短，在融合**开始之前**就必须先画出来。不是"融合完检查一下有没有堆叠"，而是"没有这张设计图，融合根本不启动"。
- **行为探针是"能不能用"的门槛**：融合产物必须真实调用、产出合格产物，才叫完成。不是"做出来再验证质量"，而是"不能真实干活的东西，压根不算融合产物"。
- 结论："更差"的产物在新体系里**没有生成路径**——堆叠被定义排除、无设计图不启动、不能真干活不算数。

---

**一句话总结**：不是给三个通病装"防线"，而是**这三个通病在新体系里各自赖以生存的那个结构，被从根上拆掉了**。上下文里没有"全量"的通道，流程里没有"绕路"的通道，融合里没有"堆叠"的通道——它不发生，不是因为被挡住，而是因为没有路。

# 二、组织架构（三级建制）

## 2.1 角色总览（名字全部保留，不更名、不借名）

```
军团级（顶层）
├── 阿极        —— 用户接口（收集需求、澄清、汇报）
├── 参谋部      —— 中枢（拆任务、调度、实时监控反馈）★ 这是主 Skill 中枢
└── 独立官员    —— 审查顾问（白帽/质检/审计/合规/根因/性能/综合）

师团级（接受参谋部分派）
└── 各级主帅    —— 能力域负责人（内容/视觉/开发/情报/进化/安全…）

普通军人岗位（挂在某主帅下）
└── 通讯员等    —— 单一职能执行岗（信息传递/状态上报等）
```

## 2.2 职责与权力边界

| 角色 | 干什么 | 不能干什么 |
|---|---|---|
| 阿极 | 收集需求、澄清、汇报、采纳官员建议 | 不亲自干活、不验收 |

**阿极澄清原则（能推断的不问、有歧义才问、问一次问到位）**：只在需求有歧义且影响结果时才提问，能推断的直接推断；避免"过度澄清"拖慢任务，也避免"瞎猜"返工。
| 参谋部 | 拆任务、调度、实时监控反馈 | 不亲自干活 |
| 各级主帅 | 管自己能力域，组织师团内执行 | 越权调度其他师团 |
| 独立官员 | 审查、提建议、反驳 | **只建议、零修改权** |
| 普通军人岗位 | 干被派发的单一职能 | 不越级、不派发 |

**权力边界三层（强制）**：
```
官员只能建议 → 用户决定 → 阿极执行
```
- 独立官员**只有建议权、没有任何修改权**（不写任何表、不派发、不否决、不裁决完成）。
- 官员建议须经"用户采纳 + 阿极转写"两步才生效，缺一即越权。

## 2.3 白帽（独立官员中最核心的一个，防迎合）

- **命名源流**：白帽取自军事建制中的**宪兵**（Military Police）——戴**白色钢盔**、执法纠错不徇私。职责 = 从用户利益出发找反例、风险、错误假设、遗漏，**反驳而非迎合**。
- **为什么必须有它**：如果没有白帽，无论 Codex 时代还是现在的模型，都会**一味迎合用户**——用户错了一直错下去。白帽是系统里唯一被授权"反驳用户"的角色。
- **默认开启、默认不独立启动**：反驳义务是人格层机制（写进阿极 persona："方案确认前必须输出假设/反例/风险/备选，不允许迎合"），0 额外成本，不拖慢任务。
- **防纯抬杠**：白帽 = 怀疑派（找反例）+ Steelman（先替用户把想法最合理的版本说出来，再攻击它）。
- 用户确认后白帽退出热路径；只有用户明确要求时，才启动隔离子 agent 做真正独立的审查。

# 三、核心运行机制

## 3.1 流水线执行（不是讨论会）

```
阿极收集需求（填需求表）
  → 参谋部把需求翻译成任务分配表（甘特图式）
  → 参谋部配发任务给多个子 agent
  → 子 agent 并行执行，各自只拿自己那份任务说明
       · 打螺丝的只知道打螺丝，装箱的只知道装箱，不需要全局上下文
  → 参谋部实时接收反馈：
       · 成功 → 汇总
       · 失败 → 再派一个，或换个角度重新派
  → 有依赖串行（上阶段完成才下阶段），无依赖并行
  → 汇总成功结果，推进下一步
```

**纪律**：
- 失败重派有**熔断上限**（同一子任务最多 3 个角度、累计 5 次无进展就停，交用户决定）——防"简单问题拖一天"复发。
- 失败重派加**冷却（cooldown）**：不是无脑立即重试，短暂冷却后再试，防雪崩；换角度基于**置信度/错误类型**判断，不是盲换。
- 子 agent **默认不互相开会**（讨论会拖慢任务）；只有用户明确要求"多堂会审"时才开临时会。
- **子 agent 三铁律**：①状态隔离（各拿各的上下文，打螺丝的只知打螺丝）②原子通信（只传结构化结果）③契约化错误处理（失败按约定格式返回，便于参谋部判断重试/换角度）。
- **参谋部自适应重规划**：执行中根据反馈调整计划（不是拆完死板执行）；拆解依据是"子 agent 能否独立执行"。

## 3.2 模型分级（按难度配智力，省费用省时间）

**核心：只定"档位"，不定"具体型号"。** 系统按角色职责划分高/中/低三档，运行时在**当前可用的模型列表**里动态选——换模型、模型迭代、某个模型下线，都只改"哪个模型属于哪档"这一张配置表，系统逻辑不动。

| 角色 | 档位 | 理由 |
|---|---|---|
| 阿极 | 低档（便宜快速） | 收集需求对话多、不需高推理 |
| 参谋部 | 高档（高智商） | 拆任务、调度、判断失败处理——最需动脑 |
| 子 agent | 按任务难度分档（低/中/高） | 简单活低档，难活才高档 |

**原则**：
1. 分级按**难度匹配**，不是"便宜优先"——防"大炮打蚊子"（贵慢）和"玩具车拉重货"（返工）。
2. **档位 = 能力契约，模型 = 运行时配置**：任何时候从"当前可用模型"里映射到各档，不写死型号。

## 3.3 表格图谱（框架 + 当前项，稀疏投影）

**核心（您最初的设想，完全正确）**：每个岗位一张表，每次只带"**整张表的标题框架 + 当前正在处理的那一项的完整内容**"。

| 岗位 | 表 |
|---|---|
| 阿极 | 用户需求表（想要什么/不要什么/约束/验收） |
| 参谋部 | 任务分配表（甘特图式：给谁/要求/输出返回格式/依赖/失败处理/状态/证据） |
| 各主帅/岗位 | 各自的工作表 |

**规则**：
1. 每次交流修改，只带：**表框架（所有标题）+ 当前项全文 + 版本指针 + 当前消息**。
2. 10 项的表正在聊第 2 项，上下文 = 10 个标题 + 第 2 项全文。
3. 可继续下潜（第 2 项再拆小项）。
4. **允许跨单元显式引用**（聊第 2 项需要第 5 项的约束时带上），但**显式、有界**——注明为什么需要、一次最多带几项，不追关联链无限扩散。
5. **稳定前缀 + 缓存命中（省 token 关键）**：表框架、军团宪法、工具目录卡这些**不变的内容放在最前且保持不变**，让它们命中提示词缓存，重复轮次几乎零成本。表框架是稳定前缀（可缓存），当前项是变化部分（不可缓存）——"框架+当前项"设计天然带来高缓存命中率。（注：缓存是否生效取决于模型供应商，需实测）

## 3.4 能力进化（自动进化闭环）

**进化 = 重生**：复制、蒸馏、融合同类能力，取长补短合成**不属于任何前身的新物种**。**学术形态**：模块化组合（SkillPacks：把能力拆成可组合模块再拼接）+ 知识嫁接（Grafting：把某技能的能力嫁接到另一技能上）——正是"取长补短"的两种成熟做法。

**自动进化闭环**：
```
打赢一场漂亮仗（成功任务）
  → 独立官员（只建议）点评：哪些招好使、哪些报错
  → 参谋部拍板：把可复用套路提纯成"新技能草稿"
  → 进化主帅审查：互补矩阵（父代优点/缺点/新决策结构）
  → 行为探针验证（真实能调用、产出合格产物）
  → 通过 → 版本化入库（可回滚）
  → 下次同类任务命中自动装配
```

**融合门禁（防"融合后比不融合差"）**：
- **互补矩阵**（证"重生"）：写清父代各自优点/缺点、新决策结构如何取长补短、删了哪些重复——这是"取长补短"的证据，不是"比高低"。
- **行为探针**（证"真能力"）：新能力真实调用、产出合格产物（callable → behavior-verified，真实产物 + SHA-256）——这是"不是纸上谈兵"的证据。
- **薄入口 + 渐进披露**：技能只挂"名字+一句话"，用到才展开详细——选项少，选择快且准（研究发现技能越多模型越选错，叫"技能遮蔽效应"）。

> **不做 A/B 同类较量**：融合目标是"原子级新能力"（父代单独都没有的新能力，如 A 有模板库 + B 有动画引擎 → 融合出"模板+动画"），这种场景下"新 vs 父A vs 父B"比高低没有意义——活不一样，无法同台较量，且"比谁强留最强"正是被否定的"替换"逻辑。**唯一例外（可选）**：当新能力是某父代的"直接升级版"（功能同质、完全覆盖）时，才需确认"升级没退化"，属少数场景，非融合核心。

## 3.5 上下文工程（结构化工程，贯穿从内到外）

> **一条原则贯穿整个系统**：一切文本——无论内部环节之间传的，还是产出去给外界的——都从诞生起就**结构化、极简、可复用、源头内建**。这不是三个孤立的东西，是同一原则应用在三个层面。底层是"上下文工程"新范式（Anthropic 为 Claude 5 代删 80% 系统提示词揭示的：从"堆规则"转向"设计结构"）。

**三个层面（互补，共享同一条根）**：

### 3.5.1 内部通信（环节之间传什么）

各环节表格 = 极简结构化字段，不是长段自然语言。

| 表 | 字段（极简、只留必要） |
|---|---|
| 阿极需求表 | 需求ID/版本 · 目标（一句）· 不要什么（一句）· 约束/优先级 · 验收标准（一句）· 状态 |
| 参谋部任务表 | 任务ID/依赖 · 给谁 · 具体要求 · 输入/输出/返回格式（代码化）· 失败处理 · 状态/证据 |

**原则**：
1. **结构 > 文字**：能用字段/表格表达，不用长段。
2. **删掉"教模型怎么做"的规则**，保留"结构、字段、边界"（模型能推断的删，模型无法自己知道的留）。
3. **参数代码化**：输入输出格式用 JSON/字段，不用自然语言描述。
4. **随模型档位调整详略**：低档模型（阿极）可稍详细，高档模型（参谋部）可极简。

### 3.5.2 代码工程（怎么写对 + 怎么被读懂）

**怎么写对（过程纪律，三件套蒸馏进开发主帅 persona，常驻非按需）**：

| 纪律 | 来源 | 内容 |
|---|---|---|
| 精简（能用一行不用两行） | [ponytail](https://github.com/DietrichGebert/ponytail) | "最好的代码是你没写的那行"；YAGNI 优先、先查标准库、能删就删 |
| 规范（资深工程师纪律） | [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills)（30K+ star） | 22 个生产级技能：规范、审查、重构、清理 |
| 正确度（不产 bug） | [superpowers](https://github.com/obra/superpowers)（187K star） | TDD、需求拷打、系统化调试 |

**怎么被读懂（语义锚点，为进化铺路）**：
- 每个函数/模块用 docstring 写清"做什么、输入输出、边界"（[Docstring Protocol](https://github.com/CoReason-AI/coreason-manifest/blob/main/AGENTS.md)）。
- 代码自带语义锚点，将来进化主帅能直接读懂、定位、蒸馏，不用猜。

**铁律**：
1. 能删就删、能复用就复用、能用一行绝不用两行。
2. 先确认需求再写代码（不确定就停下来问）。
3. TDD：先写测试再写实现。
4. 系统化调试，不盲试（见 3.6）。

### 3.5.3 对外产出（怎么被复用、被再蒸馏）

**总原则**：每个产出物从诞生起就"AI 能读懂、可复用、可被再次蒸馏融合"——这是进化的地基（乱产出无法进化）。

| 产出类型 | 规范 |
|---|---|
| 代码 | 精简 + docstring 语义锚点 + 结构清晰 |
| 元指令 | 五段式（目标/触发条件/执行步骤/边界/验收）+ 极简 |
| ComfyUI 插件等 | 遵循官方文档规范（节点说明/参数/示例，[ComfyUI 官方规范](https://docs.comfy.org/custom-nodes/help_page)） |
| 技能 | SKILL.md 标准（frontmatter + 描述 + 边界，[Anthropic 规范](https://github.com/anthropics/skills)） |
| 通用 | 带元数据（类型/用途/版本/边界）+ 可复用形态（技能/模块，非一次性文本） |

**白帽提醒**：
1. 产出规范要**内建**（产出时就规范，写进主帅铁律），不是事后补文档。
2. 规范不能拖慢——字段极简，不堆没用元数据（呼应"源头堵死"+"精简"）。
3. 按类型适配规范，不搞一刀切"万能格式"。

## 3.6 根因修复（复发驱动的有界治本）

> 目标：每次 bug 都找根因治本（不打补丁套补丁），但**不让"找根因"拖死简单任务**。核心矛盾解法：**根因官不是每次 bug 都出场，而是"复发才出场、出场就有界"**。

**流程**：
```
发现 bug
  → 先快速修复（最小正确修复，不是脏补丁）+ 记录 bug 指纹（症状+修复+位置）
  → 第一次出现 → 到此为止（记录在案，不深挖）
  → 同类 bug 第二次出现（复发）→ 触发根因官深挖（治本）
  → 深挖有界：四阶段（复现→定位→假设→验证）+ 深度上限（最多 5 层"为什么"）
  → 找到可验证根因 → 治本修复 → 根因+修复沉淀进经验库，下次直接复用
```

**四条纪律（防两个极端：不打补丁套补丁，也不无限追根因）**：
1. **复发驱动**：根因官由"同类 bug 第二次出现"触发，不是每次 bug 都出场。
2. **快修 ≠ 脏补丁**：是最小正确修复 + bug 指纹记录；同类 bug 第二次必然暴露是同一根因，逼着走治本。
3. **深挖有界**：四阶段结构化 + 深度上限，找到可验证根因就停，不追"根因的根因"。
4. **严重 bug 例外**：高风险/影响面大的 bug，第一次出现也直接深挖。

> **核心**：补丁套补丁的根源是"没记录、没复发追踪"。有了 bug 指纹 + 复发机制，同类 bug 第二次出现就暴露是同一根因，自然转治本——屎山从结构上就堆不起来。

## 3.7 安全与凭据

- **密钥铁律**：密钥不进入上下文、日志、图谱、产物，只留不透明 vault 引用；泄露即轮换（不复述、不传播、不清洗）。
- **引入外部能力前审查**：引入 skill/MCP/插件前，保卫科审查入口、脚本、依赖、权限、供应链风险。
- **最小权限原则**：子 agent 只拿完成任务所需的最小权限，不越界访问。

## 3.8 并发隔离（多子 agent 写冲突）

- **派发时划界**：参谋部配发任务时就划清"谁写哪块"——每个子 agent 只写自己独有范围的文件（从源头不冲突，不是冲突后协调）。
- **共享对象加锁**：同一可写对象同时只允许一个写入者；共享文件用写锁/乐观锁。
- 呼应"源头堵死"：冲突在派发那一刻就被设计排除。

## 3.9 任务检查点（中断恢复）

- 子任务启动时记录检查点；中断后从最近检查点恢复，不从头重做。
- 结合 DSH `sessionProjections`（状态持久化）+ 记忆文件。

## 3.10 可观测性与反馈

- **指标**：延迟/成本/成功率/上下文大小（DSH sessionTelemetry 已有，直接复用）。
- **用户反馈反哺进化**：用户对结果的 👍/👎（messageFeedback）——好评的能力保留，差评的能力触发复查/进化。

## 3.11 记忆系统（三层记忆 + 混合检索）

- **三层记忆**（Hermes 机制）：core（用户身份/偏好，长期稳定）· working（当前会话）· episodic（历史经验摘要）。
- **有界写回**：会话结束只把"验证过有用的方法"压缩成记忆条目，没用的不存。
- **混合检索**：不同记忆类型用不同检索——向量找语义相似、关键词找精确匹配、图找关系（不是单一向量检索）。

# 八、总结

**新无极军团 = 系统级自动调用（小白无感）× 能力进化重生（越用越强）× 流水线并行（快）× 模型分级（省）× 表格稀疏投影（上下文小）× 白帽反驳（防迎合）× 上下文工程（从内到外结构化）× 根因修复（复发才治本）**，全部优先构建在 DSH 原生能力上，自己只补"组织调度 + 进化治理"这一层。名字全用无极建制，外部只学方法不借名字。

**初衷两条支柱始终是第一优先级**：① 用户永远不用选技能；② 融合永远是重生，不是叠加不是替换。
