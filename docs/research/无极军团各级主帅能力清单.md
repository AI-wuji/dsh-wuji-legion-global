## 〇、各级主帅的统一机制（已验证的组织模式）

**主帅 = 领域负责人，被参谋部调度，组织该域执行。** 业界已验证的组织模式：

| 项目 | 机制 | 数据背书 | 对主帅的启发 |
|---|---|---|---|
| [multihead](https://github.com/axsar/multihead) | 把复杂任务分解，交给**专门化的 AI 组件**执行，验证结果，积累持久知识 | 有完整 README + 架构 | **主帅 = specialist，域内验证 + 积累知识**——正是"主帅"的落地模型 |

## 八、关键发现（数据说话，非臆断）

1. **每个主帅都有"带 benchmark/star 背书"的现成能力**，不是空白——开发（superpowers 187K）、设计（open-design 71 设计系统）、安全（secpriv 128 case）、搜索（Marco benchmark）、数据（InsightBench ICLR）、营销（120 skill+8门禁）、进化（37K vetted+TRACE）。
2. **"验证"有现成标准**：TRACE 评测框架、skill-validator、versuz（技能对比）、openclaw-foundry 的 S/A/B/C 评分——这些是"能力入库"的真实质量门禁，不是我们的臆断。
3. **multihead 是"主帅"的直接落地模型**：分解任务 → 专门化组件执行 → 验证 → 积累持久知识，正是主帅的完整职责。
4. **secpriv-skill 是最强的验证范例**：Facebook 官方 + 128-case benchmark + detector-validator 方法论——这应该作为"主帅能力验证"的模板（能力必须带 benchmark，不是 README 自吹）。

---

## 九、对规划的建议

1. **各级主帅 = 有 benchmark 背书的领域能力包**，不是空壳岗位——每个主帅挂上"已验证的能力 + 验证基线"。
2. **主帅能力入库必须有数据背书**：参考 secpriv-skill 的"detector-validator + benchmark"模式，能力入库带 benchmark，不是 README 自吹（呼应之前的"行为探针"）。
3. **能力验证用现成标准**：TRACE 评测 + skill-validator + openclaw-foundry 评分，不自己造评测标准。
