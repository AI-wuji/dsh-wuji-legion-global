## 二、复查发现的缺口（5 个，之前讨论过但规划里遗漏/不完整）

### 缺口一：安全与凭据（遗漏）

**问题**：之前讨论过 v11.3 的"密钥不保留、不复述、不传播、泄露即轮换"，但《完整规划》里完全没有安全/凭据章节——这是个隐患，尤其是"自动调用 MCP""外部下载"都涉及凭据。

**调研方案**：
- [OWASP Securing Agentic Apps Guide](https://entro.security/blog/practical-takeaways-from-the-owasp-securing-agentic-apps-guide/)：agent 安全实践权威指南
- [1Password：凭据风险](https://1password.com/blog/closing-the-credential-risk-gap-for-browser-use-ai-agents)：agent 凭据管理
- [Agent secret handling patterns 2026](https://safeguard.sh/resources/blog/agent-secret-handling-patterns-2026)：密钥处理模式

**补进规划**：新增"安全与凭据"小节——密钥不进入上下文/日志/图谱，只留 vault 引用；泄露即轮换；引入外部能力前保卫科审查。

### 缺口二：并发写冲突（遗漏）

**问题**：多子 agent 并行执行时，若同时写同一文件/对象，会产生冲突。3.0 文档有"同一可写对象同时只能一个写入者"，但规划没落地。

**调研方案**：
- [agentlocks](https://github.com/simke9445/agentlocks)：文件锁，让多个 AI agent 共享一个 Git 工作区
- [Lock-Free Concurrency（乐观并发控制）](https://github.com/nexi-lab/nexus/issues/184)：乐观锁
- [MCP 代理协调员](https://www.mcpworld.com/zh/detail/97058c778145d0ad7b6f31cecb0b9aa4)：多 agent 并行协调

**补进规划**：流水线执行加一条——**每个子 agent 写自己独有范围的文件，共享对象加写锁/乐观锁；参谋部派发时就划清"谁写哪块"，从源头不冲突**（呼应"源头堵死"）。

### 缺口三：任务级失败恢复（不完整）

**问题**：3.6 只讲了 bug 根因修复，没讲"整个任务中断/会话断开后的恢复"（检查点、从断点继续）。

**调研方案**：
- [agent-checkpoint-mcp](https://pypi.org/project/agent-checkpoint-mcp/)：本地检查点，任何 agent 从断点恢复多步计划
- [Amazon Bedrock Session Management](https://aws.amazon.com/cn/blogs/machine-learning/amazon-bedrock-launches-session-management-apis-for-generative-ai-applications-preview/)：会话管理 API
- [Eino Session Checkpointing](https://cloudwego.cn/docs/eino/release_notes_and_migration/eino_v0.5._-adk_implementation/)：会话检查点 + 暂停/恢复

**补进规划**：新增"任务检查点"——子任务启动时记录检查点，中断后从最近检查点恢复，不从头重做。

### 缺口四：可观测性与反馈回路（不完整）

**问题**：性能官、反馈回路只是 P5 提了一句，没有系统化（运行时监控、日志、指标、用户反馈怎么反哺）。

**调研方案**：
- [AI Agent Observability](https://uptrace.dev/blog/ai-agent-observability)：agent 可观测性（指标/日志/追踪三大支柱）
- [Evaluation-Driven Development of LLM Agents](https://arxiv.org/html/2411.13768v3)：持续评估与适配的流程模型
- [Datadog LLM Observability](https://www.datadoghq.com/product/ai/llm-observability/)：LLM 可观测性

**补进规划**：新增"可观测性"——延迟/成本/成功率/上下文大小指标（DSH sessionTelemetry 已有），用户反馈（messageFeedback）反哺进化。

### 缺口五：多模型切换的 DSH 具体机制（不落地）

**问题**：3.2 说"档位=契约、模型=运行时配置"，但没落到 DSH 具体怎么配。

**补进规划**：明确 DSH 落点——`agentDefaultModel`（默认档）+ `subagent` 指定 model（子 agent 分档）+ provider 配置（可用模型列表）；档位映射表是一份运行时配置。

## 三、补进规划的内容（新增 §3.7 安全凭据、§3.8 并发隔离、§3.9 任务检查点、§3.10 可观测性）

### 3.7 安全与凭据
- 密钥不进入上下文/日志/图谱/产物，只留不透明 vault 引用；泄露即轮换。
- 引入外部能力（skill/MCP/插件）前，保卫科审查入口/脚本/依赖/权限。
- 最小权限原则：子 agent 只拿完成任务所需的最小权限。

### 3.8 并发隔离（多子 agent 写冲突）
- 参谋部派发时就划清"谁写哪块"——每个子 agent 写自己独有范围的文件。
- 共享对象加写锁/乐观锁；同一可写对象同时只允许一个写入者。
- 从源头不冲突（派发时划界），不是冲突后协调。

### 3.9 任务检查点（中断恢复）
- 子任务启动时记录检查点；中断后从最近检查点恢复，不从头重做。
- 结合 DSH sessionProjections（状态持久化）+ 记忆文件。

### 3.10 可观测性与反馈
- 指标：延迟/成本/成功率/上下文大小（DSH sessionTelemetry）。
- 用户反馈（messageFeedback：👍/👎）反哺进化——好评的能力留，差评的能力触发复查。

## 四、结论

1. **一致性无问题**：之前反复调整的三点（防御→源头堵死、写死型号→档位、A/B→互补矩阵）都已闭环，无残留。
2. **发现 5 个缺口**：安全凭据、并发隔离、任务检查点、可观测性、多模型 DSH 落地——前三个是遗漏（之前讨论过但没进规划），后两个是不完整。
3. **全部有对症方案**（OWASP/agentlocks/checkpoint-mcp/observability 等）。
4. **补进规划后**：新增 §3.7-3.10，规划从"核心机制"补全到"工程完整性"（安全、并发、恢复、可观测）。
