## 2. 适配结论：哪些东西适合搬进 DeepSeek Harness

### 2.1 直接可用、几乎零改造成本 ✅

| 无极资产 | DSH 落点 | 方式 |
|---|---|---|
| `capabilities/*/manifest.json` 触发词表 | DSH skill 目录描述的语义锚点 | 把 17 个能力包的 `triggers` 转写进 DSH skill 的 `description`，让 skill 自动装载命中率大幅提升 |
| `wuji.exe` 确定性路由 | 宿主内 `wuji` 服务 | 通过 `ctx.subprocess` 或 pwsh 调用 `wuji route / context-select / verify`，把已验证的路由逻辑直接变成 DSH 工具 |
| `SKILL.md` 路由热路径规则 | 系统级 agent 指令 | 保留为系统级 skill；本质是把"选什么能力"交给模型+确定性路由双保险 |
| `scripts/verify-*.ps1` 行为探针 | 能力验证工具 | 融合新插件后用同一探针做行为验证（callable → behavior-verified） |
| 融合基因组 / 进化主帅文档 | 新插件融合流程的"物种谱系"模板 | 定义融合插件时记录 `fusion_genome`（父代、版本、适配器、资产契约） |

### 2.2 需要适配改造 🔄

| 无极资产 | 差异 | 适配方案 |
|---|---|---|
| Go CLI 的路由 JSON | 面向 Codex 的 `model_class`（Luna/Terra/Sol）与 `gpt-5.6-*` 委派 | 保留触发词/能力/入口部分；**模型分工改为 DSH 原生机制**（subagent / workflow / goal），不引入 GPT 层级 |
| 参谋本部（staff）常驻模型实例 | Codex 需要真实子代理证明模型执行 | DSH 已有 `subagents` 注册表 + `workflowEngine` + `goal`，天然取代"staff 实例"：调度 = 本 agent 的 goal/todo，执行 = subagent |
| 能力包 = 目录+SKILL.md | DSH 能力 = cordis 插件 + skill 目录 | 能力包统一表达为"**DSH skill（指令层）+ cordis 插件（服务/工具层）**"双层注册 |

### 2.3 不该搬 / 需谨慎 ⚠️

| 资产 | 原因 |
|---|---|
| `wuji route` 的 GPT 模型层级委派 | DSH 模型路由是宿主的 `llm` 服务与 `agentDefaultModel`，不能由 skill 层伪造"模型切换证据" |
| 需求图/执行图的完整 Go 存储实现 | DSH 已有 `goal`（会话日志持久）、`todo`、`session` 持久化；重复造图谱会引入新状态源，只在融合治理需要时才引入 |
| `officer-select` MoE 官员 | DSH 审批栈 + 子代理已覆盖"独立验证"；如需官员视角，用一次独立 subagent 即可，不需要新系统 |

## 3. 落地蓝图（三阶段）

### 阶段 A：系统级自动路由器（初心 ① 的核心）

**目标**：用户说"帮我整理一下飞书里的这个表格，再做成 PPT 发到群里"——系统自动装载 lark-sheets → dashi-ppt/wuji-deck → lark-im，用户全程不知道"skill"是什么。

**A1. 能力索引（Capability Index）**
- 新建宿主侧注册表：一份 `capabilities.registry.json`（DSH 版 manifest），每条 = `{ id, triggers[], entrypoint(工具/skill), verify(探针), fallback }`。
- 数据来源：先导入 Codex 2.1 的 17 个 manifest（触发词直接复用），再映射到 DSH 已装能力（27 个 lark-* + dashi-ppt + wuji + cordis）。

**A2. 路由服务（wuji-dsh 插件，宿主侧）**
- 用 cordis 插件实现 `wuji` 服务：`route(query) -> { capability, skills[], tool[], context_hint, verify }`。
- 规则：确定性触发词优先（来自 registry），未命中再走模型判断（skill 描述语义匹配）；结果注入 `systemPrompt.section()` 或返回给 agent 按指引行动。
- 复用 `wuji.exe route` 作为可选的确定性对照/校验实现（`ctx.subprocess` 调用），初期两者并存、以探针对齐。

**A3. skill 目录语义化**
- 把每个已装 skill 的 description 按"触发词 + 边界 + 入口"重写，使 skill 自动装载命中率提高（这是"自动调用"最省成本的一层）。

**A4. 小白入口（用户不可见的层）**
- 不向用户暴露"请选择 skill/MCP"；所有选择发生在系统层。用户看到的只是结果与（可选的）执行过程说明。
- 需要交互时才提问，且问题用业务语言（"这个表格要保留哪些列？"），不是"你要用 lark-sheets 吗？"。

### 阶段 B：能力蒸馏与融合（初心 ② 的核心）

**目标**：同类能力合并成更强插件。

**B1. 能力审计工具（wuji-ev 插件或 workflow）**
- 盘点已装 skills/tools/MCP，按能力域聚类，输出重复/互补矩阵（如：PPT 域 = dashi-ppt + wuji-editable-deck + wuji-web-deck + baoyu-slide-deck；写作域 = khazix + humanize + baoyu-translate；检索域 = baoyu-url-to-markdown + youtube-transcript + electron-extract）。
- 对每个域给出结论：`融合提案 / 仅借鉴 / 拒绝 / 待证`（沿用进化主帅规则）。

**B2. 融合为 DSH 原生插件**
- 用 `cordis_define` 定义融合插件包（Host/Client 双侧或单侧），把父代入口收敛为统一入口；资产（模板、脚本）完整继承并登记 asset_id/版本/兼容条件（沿用融合基因组）。
- 示例（首批候选）：
  1. **lark 全家桶 → 飞书统一插件**：27 个 lark-* 收敛为一个飞书能力插件（统一认证 + 域路由），技能保留为指令层，服务层合并；
  2. **演示域融合 → wuji-deck 插件**：dashi-ppt + wuji web-deck/editable-deck + baoyu-slide-deck 合并为单一"做演示"入口（可编辑 PPTX + HTML 双引擎）；
  3. **内容提取融合**：url→markdown / youtube 字幕 / electron 提取 / x→markdown 合并为"网页内容提取"统一插件。

**B3. 行为验证门禁**
- 融合插件必须先过探针：`callable`（入口能跑）→ `behavior-verified`（真实 fixture 产物 + SHA-256 证据），沿用能力契约；不过门禁不进入默认热路径。

### 阶段 C：治理与长期演化（可选但推荐）

- **能力生命周期状态机**：`known → callable → behavior-verified → primary` 落到 registry，任何"已融合"声明必须有证据句柄。
- **失败经验复用**：DSH 的 goal/session 持久化已经提供；后续可加"失败→能力缺失→检索经验"钩子（`tools/result` 事件）。
- **用户反馈回路**：用 `messageFeedback` 服务记录"用户对某能力结果的 👍/👎"，作为能力替换的输入证据。

## 4. 技术实现要点（给 DSH 工程侧的钩子清单）

| 要实现的事 | 用到的 DSH 机制 |
|---|---|
| 路由注入每步上下文 | `systemPrompt.section()` / `system-prompt/assemble` 事件 |
| 自动装载正确 skill | `skills.registerProvider` / skill 目录 description 语义化（已存在 `tool-skill` 自动装载） |
| 确定性路由对照 | `ctx.subprocess` 调 `wuji.exe route`；或纯 Node 重写触发词匹配 |
| 融合插件定义/运行 | `cordis_define` + `cordis_run`（Host+Client 双侧）；Inspect 查询真实 Service/Tool 契约 |
| 能力验证 | `scripts/verify-*.ps1` 通过 pwsh 运行，产物 + SHA-256 |
| 并行执行（融合审计） | `workflow`（多能力域并行审计）+ `subagent` 后台派发 |
| 长任务（融合+验证） | `create_goal` / `update_goal` 持久化进度 |
| 权限 | 融合插件首次运行走现有 approval 栈（当前 danger-full-access 已放行） |

## 6. 关键结论

1. **初心 ① 已具备 80% 的底层**：DSH 的 skill 自动装载 + 宿主扩展点天然支持"系统级自动调用"，缺的只是一层**确定性能力路由**（注册表 + 路由服务），以及把选择过程完全移出用户视线。
2. **初心 ② 的模板已存在**：Codex 2.1 的融合基因组、进化主帅规则、行为探针体系可以直接搬；DSH 的 cordis 插件机制提供了比 Codex 更干净的"新插件"容器（define/run/stop/undefine + Inspect 验证）。
3. **最大杠杆点是飞书域**：27 个 lark-* 技能共用同一 lark-cli 底座，是最典型的"同类能力蒸馏融合"场景，也是小白用户最高频场景（文档/表格/消息/日程）。
4. **不要照搬 Codex 的模型层级**：DSH 用 subagent/workflow/goal 原生机制承担调度与执行，避免引入 GPT 层级和"模型切换证据"问题。
5. **验证是融合的唯一通行证**：任何"更强的新插件"必须过行为探针（callable → behavior-verified）才能进入默认热路径，防止只做表面合并。
