# 无极军团 · 产出物规范专项调研（产出物也要 AI 友好）

> 版本：v1.0
> 日期：2026-08-15
> 触发：用户提出——不只是内部执行要规范提示词，**产出物**（代码、元指令、ComfyUI 插件等）也要规范，让产出本身就标准、可读、可复用。
> 结论：这正是"**为 AI 而写的文档/产出**"这个新领域——产出物不仅人要能读，AI 也要能读、能理解、能复用。无极军团要进化，就必须让产出的东西"**天生可被再次蒸馏融合**"。

---

## 一、核心洞察：产出物要"AI 友好、可复用"

无极军团的核心是"进化"——产出的代码/技能/插件，将来可能被再次蒸馏、融合成更强的能力。**如果产出时就是乱的（屎山代码、无文档、无元数据），将来就无法进化**。

所以产出物规范的本质是：**让每个产出物从诞生起就"可被 AI 读懂、复用、蒸馏"**。这不只是"整洁"，是"进化的地基"。

---

## 二、可借鉴的方案

| 方案 | 机制 | 融合点 | 裁决 |
|---|---|---|---|
| [SAGE 规范（Structured Agent Guidance Embeddings）](https://github.com/mikewcasale/sage-spec) | 人↔AI 协作代码库的**文档标准**：结构化 agent 引导嵌入 | **产出物文档标准**：定义"人 + AI 都能读懂的代码文档格式" | **融合提案** |
| [Docstring Protocol（AST 原生语义锚定）](https://github.com/CoReason-AI/coreason-manifest/blob/main/AGENTS.md) | 用 docstring 做"语义锚点"，让代码结构和语义对 AI 可检索 | **代码产出规范**：代码里的注释/文档就是 AI 的检索锚点 | **融合提案** |
| [Facebook DocAgent（ACL 2025）](https://github.com/facebookresearch/DocAgent) | 多 agent 分层自动生成高质量代码文档 | **自动生成文档**：产出代码后自动生成上下文感知的文档 | 仅借鉴 |
| [ComfyUI 官方节点文档规范](https://docs.comfy.org/custom-nodes/help_page) | 官方定义 custom node 的文档格式（节点说明/参数/示例） | **ComfyUI 插件产出规范**：节点描述、参数说明按官方标准写 | **融合提案** |
| [SKILL.md 规范（Anthropic 开放标准）](https://github.com/anthropics/skills) | 技能包的可移植、版本化标准 | **技能产出规范**：每个技能按 SKILL.md 标准写（frontmatter + 描述 + 边界） | **融合提案** |
| [skillrail（版本化技能源）](https://github.com/gbouziden/skillrail) | 一份版本化源，编译到多个平台 | 产出物的版本化、多平台 | 仅借鉴 |
| [Dossier Specification](https://raw.githubusercontent.com/imboard-ai/ai-dossier/refs/heads/main/docs/reference/specification.md) | AI 产出物的结构化档案规范 | 产出物元数据规范 | 仅借鉴 |

## 三、无极军团的产出物规范设计（按产出类型）

**总原则：每个产出物都附带"AI 能读懂的元数据 + 结构化说明"，让它将来可被再次蒸馏融合。**

### 3.1 代码产出（治屎山，为进化铺路）

```
代码规范（写进开发主帅铁律）：
├── 精简：能删就删、能用一行不用两行（ponytail）
├── 语义锚点：每个函数/模块用 docstring 写清"做什么、输入输出、边界"（Docstring Protocol）
├── 结构清晰：模块化、单一职责，不堆大泥球
└── 自文档化：代码本身 + 最小必要注释，让 AI 和人都能读懂
```
- 核心：代码产出**自带语义锚点**，将来进化主帅能直接读懂、定位、蒸馏，不用猜。

### 3.2 元指令产出（meta-instruction）

```
元指令规范：
├── 结构化：目标 / 触发条件 / 执行步骤 / 边界 / 验收 五段式
├── 极简：只留必要字段，不写解释性废话
└── 可复用：作为"技能"的形态存在（SKILL.md 格式），而非一次性文本
```

### 3.3 ComfyUI 插件等专项产出

```
插件/节点产出规范：
├── 遵循官方文档规范（如 ComfyUI 节点文档：说明/参数/示例）
├── 节点描述清晰、参数有类型和默认值说明
└── 附带使用示例（让 AI 和人都会用）
```

### 3.4 通用产出物规范（所有产出统一）

| 规范项 | 内容 |
|---|---|
| **元数据** | 每个产出物带：类型/用途/版本/作者/边界 |
| **结构化说明** | 输入输出格式、依赖、使用方式 |
| **可复用形态** | 优先以"技能/模块"形态产出（SKILL.md/插件），而非一次性文本 |
| **语义锚点** | 关键部分有可检索的说明（docstring/节点文档/字段说明） |

## 四、白帽的提醒

1. **产出规范要"内建"，不要"事后补"**：产出时就用规范格式写（铁律写进主帅 persona），而不是产出完再补文档（那样又回到"事后防御"）。
2. **规范不能拖慢**：极简是前提——规范字段只留必要的，不为了规范而堆一堆没用的元数据（否则又违反"源头堵死"和"精简"）。
3. **产出规范 = 进化的地基**：规范产出物不是为了"好看"，是为了"将来能被进化主帅读懂、蒸馏、融合"。没有规范产出的系统，进化不了。
4. **按产出类型适配规范**：代码用 docstring、插件用官方文档规范、技能用 SKILL.md、元指令用五段式——不搞一刀切的"万能格式"。

---

## 五、结论

1. **用户洞察正确**：产出物也要规范——不只是"整洁"，是**进化的地基**。
2. **核心原则**：每个产出物从诞生起就"可被 AI 读懂、复用、蒸馏"，自带语义锚点和元数据。
3. **按类型规范**：代码（docstring 语义锚点）、元指令（五段式）、插件（官方文档规范）、技能（SKILL.md）。
4. **产出规范是"内建"的**：写进各主帅铁律，产出时就用规范格式，不是事后补。
5. **与"精简""源头堵死"一致**：规范字段极简、只留必要，不堆没用元数据。
